# New benchmark suite

The artifacts with `_new` in the filename are generated by the current
reproducible runner on the native core. The legacy SEC1–SEC10 drivers and their
outputs were removed (git history only); they are not current evidence.

## Inputs and conversion

The run discovers `.y4m` files under `data/raw`. The recorded runs used nine
clips; only `foreman_cif.y4m` is tracked, so a fresh clone produces 3 media
cases (one clip × three resolutions) instead of 27. It first converts every source
in full at its native resolution to Annex-B H.264 under
`benchmark/results/converted_h264_new/`; `conversion_manifest_new.json` records
verified frame counts, source frame-rate rational, playback duration at that
rate, timings, sizes and hashes (raw Annex-B streams do not carry container
timestamps). It then
runs pipeline/quality measurements on the first 30 frames of every source at
352×288, 640×480 and 1280×960, writing benchmark H.264 files under
`benchmark/results/media_new/<run-id>/encoded_h264/` at 352×288,
640×480 and 1280×960. The latter two are scaled from CIF source material; they
measure decoder/embedder scaling, not natural high-resolution scene behavior.
Encoding is pinned to libx264 Baseline/CAVLC, QP 22, all-intra, no B-frames,
one thread and one slice per IDR. One thread/one slice is important: FFmpeg's
automatic multi-slice output is outside the native path's supported contract.

The 30-frame pipeline window is intentionally bounded because an observed
1280×960, 300-frame capacity scan exceeded 11 minutes on this host before embed
began; the full-duration native-resolution conversion is retained separately.

Each media row passes only when native capacity measurement, native authenticated embed, FFmpeg strict
decode (`-v error -xerror`), blind extraction with the correct key, and
rejection with a wrong key all succeed. Capacity is measured by the native
scanner. Performance reports include encode/embed time, embed FPS, sampled
child CPU/RSS, output sizes and per-frame PSNR-Y/SSIM. Quality is reported both
against decoded source Y4M (compression plus embedding) and against the clean
H.264 encode (incremental embedding effect).

## Metric glossary

- `Full sec` / `source_duration_seconds`: duration of the entire original Y4M
  clip, calculated as source frame count divided by its source frame rate. It is
  not the benchmark runtime. Raw Annex-B H.264 has no container timestamps, so
  the exact source frame-rate rational is recorded in the conversion manifest.
- `Encode ms`: wall time for FFmpeg to convert the benchmark window (30 frames)
  from Y4M to H.264 at that row's target resolution. Full-duration native-size
  conversion times are separately in `conversion_manifest_new.json`.
- `Capacity ms`: wall time for the native scanner to read the benchmark H.264
  and count eligible CAVLC candidate bits. It is a separate preflight/diagnostic
  measurement, not included in `Embed ms`.
- `Embed ms`: elapsed time from launching the native embed process through
  supplying the sample stream and receiving completion. `FPS*` is the 30
  encoded sample frames divided by this wall time; it excludes camera capture
  and is not end-to-end camera FPS.
- `CPU s`: cumulative CPU seconds observed for the native embed child while it
  runs. `RSS MB`: highest sampled resident memory of that child, in decimal MB;
  the 5 ms sampler can miss short peaks. Neither is total machine resource use.
- `Gate`: `passed` requires candidate-capacity measurement, successful embed,
  strict FFmpeg decode, exact payload recovery with the right key, and rejection
  with a wrong key.
- `Source PSNR μ` / `PSNR min`: arithmetic mean and minimum finite per-frame
  luma PSNR comparing decoded source Y4M to decoded stego H.264. This includes
  lossy H.264 conversion as well as embedding. Infinite PSNR from identical
  frames is counted separately and excluded from the finite mean/min.
- `Source SSIM μ` / `SSIM min`: mean and minimum frame SSIM for the same
  source-to-stego comparison; values closer to 1 indicate greater structural
  similarity.
- `Embed PSNR min` / `Embed SSIM min`: minimum finite per-frame measures
  comparing the clean H.264 decode to the stego H.264 decode. These isolate the
  incremental effect of embedding; infinite PSNR frames are identical before
  and after embedding. Inspect the CSV for every frame rather than relying on
  averages alone.

On the recorded run `media_new/20260924T150707Z_2be60c`, 29/30 frames in each case were unchanged by embedding.
The modified-frame PSNR was below the historical 40 dB floor in 13 of 27
cases; the worst was 32.76 dB (`hall_monitor_cif.y4m`, 1280×960). Functional
pipeline pass does not mean visual-quality pass. This is why the quality PDF
has a separate 40 dB reference column. The earlier run `20260924T144703Z_840091`
had 15/27 cases below 40 dB (worst 34.13 dB); it is kept for comparison only.

## Run commands

```powershell
py -3.12 -m benchmark.run_new_suite          # everything below in one run
py -3.12 -m benchmark.crypto_benchmark_new
py -3.12 -m benchmark.media_benchmark_new
py -3.12 -m benchmark.zkp_benchmark_new
py -3.12 -m benchmark.reports_new
```

Named deliverables are:

- `benchmark/results/performance_new.pdf`
- `benchmark/results/video_quality_new.pdf`
- `benchmark/results/security_new.pdf` and `security_new.json`
- `benchmark/results/zkp_new.pdf` and `zkp_new.json`
- `benchmark/results/media_new/<run-id>/video_pipeline_new.json`
- `benchmark/results/media_new/<run-id>/quality_per_frame_new.csv`
- `benchmark/results/conversion_manifest_new.json`
- `benchmark/results/converted_h264_new/*__full__qp22_allintra_new.h264`
- Converted source encodes and stego streams are in that media run's
  `encoded_h264/` and `stego_h264/` directories.

Security records are actual `cryptography` seal/sign and open/verify calls for
HMAC-SHA-256, Ed25519, RSA-PSS, AES-256-GCM, ChaCha20-Poly1305,
RSA-OAEP+AES-GCM, X25519+HKDF+ChaCha20-Poly1305, and an Ed25519
encrypt-then-sign composition. MAC, signature and encryption properties are
not equivalent. The latter two are explicitly not claimed to be standardized
signcryption; no unaudited custom construction is mislabeled as such.

The proof comparison executes Groth16 and PLONK on the same R1CS and witness,
including positive and tampered-public-input verification. The PLONK runner
measures a locally generated adequately sized Powers-of-Tau transcript and
PLONK setup separately. The old `sec5_zkp_data.json` was not valid comparative
evidence: it mixed a different ZK-Schnorr statement with simulated/literature
values, so those outputs have been removed.

### Further ZKP systems to benchmark fairly

Only systems proving the same payload-commitment statement should be compared
as like-for-like circuit proofs. Practical next candidates are:

- **Halo2 (IPA backend):** reimplement the existing SHA-256 commitment relation
  in Halo2's Rust circuit API; report arithmetization/setup differences.
  [Official Zcash Halo2 source](https://github.com/zcash/halo2).
- **RISC Zero zkVM (STARK/FRI):** implement that same relation as a Rust guest
  program and benchmark guest execution, receipt/proof generation, and verify
  separately. This is a verifiable-computation comparison, not a direct R1CS
  constraint-count comparison. [Official RISC Zero docs](https://dev.risczero.com/).
- **Bulletproofs R1CS:** possible as an experimental comparison, but the
  upstream R1CS API is explicitly marked experimental/unstable; it should not
  be presented as a production-ready alternative without qualification.
  [Upstream Bulletproofs project](https://github.com/dalek-cryptography/bulletproofs).

The current Windows environment has no `rustc` or `cargo` installed, so none of
these Rust systems has been built or measured here yet. Do not reuse the old
SEC5 numbers as substitutes.

The current native streaming path authenticates payloads with HMAC. The ZKP
benchmark is a separate proof-generation/verification stage; it does not imply
that proof generation runs in the camera pixel path or that the circuit proves
camera origin/full-video integrity. Sampled process RSS can miss brief peaks.
